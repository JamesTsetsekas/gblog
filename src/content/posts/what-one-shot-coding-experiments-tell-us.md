Give five coding agents the same brief for a taxi game. Each has to decide how the car handles, how a passenger boards, what the route guidance shows, and what happens when time runs out. Then give those agents a brief for a graphic that lets someone compare clear nights across eight observing sites. Both jobs involve code, design, and judgment about what to test. Playing the resulting game and trying to answer a question with the chart tell you more about those decisions than the agent's summary alone.

That's what I wanted from [Oneshot Arcade](https://jamestsetsekas.github.io/oneshot-arcade/) and [Oneshot Visuals](https://jamestsetsekas.github.io/oneshot-visuals/). They make the prompt, artifact, and evidence available together. A comparison gets interesting when you can say what a particular build did with a particular brief.

## What counts as one shot?

In these projects a shot is a coding-agent session started with one task brief and a common set of instructions. Inside that session the agent can write and revise code, run its own checks, and inspect its own work. The Arcade harness even requires a verification report and calls for a gameplay screenshot from the production build. It records a wrapper version because the operational instructions changed during the project. Version 1.1 added an explicit rule that ending the turn ends the attempt, after a session had needed a continuation nudge while waiting for a background command. [Arcade harness](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/prompts/ONESHOT-HARNESS.md)

The Arcade matrix has eight original browser game briefs across five configurations, or 40 build entries. The briefs range from Shardfront's real-time strategy and Ashfall Covenant's action RPG to Meridian Run's open-world courier adventure and Farestorm's taxi driving. The lineup pairs GPT-6 Astra and GPT-6.1 Sol with Codex, and Fable 5.2, Opus 5.5, and Sonnet 5.5 with Claude Code. The catalog labels the effort high. Eight Astra entries predate the common harness, and four of those are marked iterated because they were remade or retained from an earlier attempt. I would keep their history visible when comparing game outputs. [Arcade repository and lineup](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/README.md)

The harness asks for a playable vertical slice of deliberately large game designs. That's a useful constraint because scope decisions leave a trace. The Sol Farestorm report describes a single timed shift in a small procedural district, with pickup, delivery, scoring, and retry. It records several of its choices, including a custom planar controller, twelve destinations, and omitted modes. The underlying simulation has code for fares, traffic, movement, and rank. The report says the authoring agent ran twelve tests and observed one delivered fare in Chromium. Those checks are reported by the entrant. A comparison should preserve that attribution alongside the source and the larger brief. [Farestorm brief](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/prompts/games/08-farestorm-browser-arcade-driving.md), [Sol build report](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/builds/gpt-6.1-sol-high/farestorm/ONESHOT-REPORT.md), [Simulation source](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/builds/gpt-6.1-sol-high/farestorm/src/sim.ts)

## Visuals gives you different things to check

Visuals is a separate 30-entry pilot. Its six briefs span two static SVG illustrations, two deterministic animations, and two interactive graphics. Glasshouse at Blue Hour and Kestrel Hand Pump test static composition and illustration. Straight-Line Linkage and The Last Ferry give motion a time dimension. Clear Skies Ledger and Ripple Rail add user-controlled state. Entries were made in fresh T3 sessions using Codex or Claude at high effort. The shared contract asks for self-contained HTML with inline SVG, with fixed-time rendering via `?t=` for the animated briefs. The repository also includes historical planning drafts for a larger study. The README and implemented catalog describe the pilot that actually ran. [Visuals README](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/README.md), [Prompt catalog](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/catalog/prompts.json), [Visuals contract](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/prompts/VIS-CONTRACT.md)

A look at Clear Skies Ledger shows why the rubric has to follow the task. The brief provides 96 synthetic observations, along with sorting, filters, and focus behavior. The Astra source builds an SVG heatmap and recomputes the monthly totals from visible rows. The source makes that choice inspectable. It still takes an interaction check to tell whether a reader can use the control, understand the resulting state, and answer the question on screen. [Clear Skies Ledger brief](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/prompts/VIS-P5.md), [Astra artifact source](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/builds/VIS-P5/astra/index.html)

A small review starts with a concrete expected result. Filter the chart to Bortle classes 1 through 3. January's total should become 67, the sum of the four eligible rows in the brief, and Larch Basin should show the fewest clear nights among those rows, at five. Try answering by keyboard as well. See where focus lands after a row disappears. For an animated piece I would check a few prescribed poses and the transition across the loop boundary. A poster can establish how a single frame looks. Those other checks need the running artifact.

## Keep the evidence in view

Arcade publishes author test counts, coverage notes, and self-scores. Those can tell you where to look or what to reproduce. Each entrant can choose different tests, so a count alone cannot compare coverage. Visuals records technical capture results and leaves the catalog scores empty. The dashboard supports blind pairs and keeps a viewer's ratings and picks in browser-local storage with JSON import and export. Generated source is offered as text, with live preview on request in a sandboxed frame. Capture and a personal preference answer different questions. Neither operation checks all of the geometry, interaction, or accessibility requirements in a brief. [Arcade README](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/README.md), [Visuals README](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/README.md), [Visuals run catalog](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/catalog/runs.json)

There are limits to what the setup can isolate. The workspace boundaries during agent runs depend on instructions. Agent defaults and tool access differ, and a shared effort label provides no common compute budget. Visuals also documents a safety-only instruction to still-running Claude sessions after an entrant reported broad Chrome process cleanup. The README says the instruction concerned only the processes sessions started. Concurrent runs, scheduling, and tool delays make elapsed times a poor basis for a speed ranking. Visuals has one attempt per pairing; Arcade includes the four documented iterated entries. Neither collection supplies comparable repeated trials from which to estimate run-to-run variation. [Arcade fairness notes](https://github.com/JamesTsetsekas/oneshot-arcade/blob/1fb964814e1d6971d1dfa8232a4d20e789cc6930/README.md#fairness-and-honesty-notes), [Visuals methodology caveats](https://github.com/JamesTsetsekas/oneshot-visuals/blob/a29fa29a266dad7ac763064eb2d0bc313ef31d8c/README.md)

The best way into either collection is to pick one brief, choose one behavior you care about, and try it on two builds. For Farestorm, I would try the whole cycle from pickup to delivery to a fresh shift. For Clear Skies Ledger, I would check the filtered total and how clearly the graphic communicates which rows contributed. Open the report or source after trying it. You may learn that you prefer different approaches on different tasks, and you can point to the behavior that made the difference.
